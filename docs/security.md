# Безопасность VETMO

Документ описывает, какие ключи и данные публичны, как разграничен доступ
в Supabase и что проверяется при сборке.

## 1. Публичные и секретные ключи

| Ключ | Где используется | Секрет? |
|---|---|---|
| `anon` / `publishable` | пользовательское приложение, чтение справочных данных | нет |
| `service_role` | VETMO Admin, скрипты синхронизации | да |
| STRATZ token | скрипты синхронизации, VETMO Admin | да |

Публичный ключ Supabase вшивается в `VETMO.exe`. Он не даёт права записи
в справочные таблицы: доступ ограничен политиками Row Level Security.
Секретные ключи в пользовательскую сборку не попадают.

Секреты хранятся в `%APPDATA%\VETMO\secrets.env` вне репозитория и вне
OneDrive. Шаблон переменных — `installer/ADMIN-SETUP.txt`.

## 2. Row Level Security в Supabase

Для таблиц `vetmo_*` включён RLS.

- `anon` и `authenticated` могут читать справочные таблицы: героев, патчи,
  мету, матчапы, бан-статистику, новости и журнал синхронизации.
- Политик на запись для `anon` нет: `INSERT`, `UPDATE` и `DELETE` в справочные
  таблицы запрещены.
- Пользовательские настройки и драфты привязаны к анонимной сессии и доступны
  только её владельцу.
- `service_role` обходит RLS. Он используется только Admin-приложением и
  sync-скриптами, которые запускает сопровождающий.

Проверить политики можно в Supabase Dashboard → Authentication → Policies
или запросами из `docs/supabase-setup.md`.

## 3. Сборка пользовательской версии

`vetmo.spec` собирает только пользовательский entry point. В граф импортов
не входят `vetmo.admin`, `vetmo.services.stratz_sync`, `vetmo.services.stratz_client`
и модуль чтения sync-секретов. Сборочный скрипт дополнительно проверяет,
что в `dist/VETMO.exe` нет:

- имён и значений sync-переменных;
- строк `service_role`, `stratz_sync`, `stratz_client`, `vetmo.admin`;
- значений из локального `%APPDATA%\VETMO\secrets.env`.

Админская сборка содержит эти модули, но не содержит значений секретов.
Секреты читаются во время запуска из файла пользователя.

## 4. Локальные данные

- Настройки оверлея и драфты: `%APPDATA%\VETMO\settings.json`,
  `%APPDATA%\VETMO\drafts.json`.
- Локальная база: `vetmo.db` в рабочей папке приложения.
- Логи: `%APPDATA%\VETMO\logs`.
- Кэш иконок: `assets/cache`.

В этих файлах нет `service_role`, STRATZ-токена и паролей Supabase.

## 5. Сеть

Приложение работает по HTTPS. Поддерживается системный прокси Windows и
переменные `HTTP_PROXY` / `HTTPS_PROXY`. Для запросов к OpenDota и STRATZ
используются только публичные эндпоинты; секретные ключи передаются
в заголовках и не пишутся в логи.

## 6. Если ключ попал в публичный доступ

1. Перевыпустить ключ в Supabase Dashboard → Project Settings → API.
2. Перевыпустить STRATZ-токен в кабинете STRATZ.
3. Обновить `%APPDATA%\VETMO\secrets.env` на машинах сопровождения.
4. Проверить журнал `vetmo_sync_runs` на подозрительные запуски.
5. Пересобрать Admin-версию, если ключ мог попасть в артефакт.

Публичный `anon`-ключ перевыпускать не обязательно: он предназначен для
клиентских приложений, а запись ограничена RLS. Но если ключ скомпрометирован
вместе с политиками, его также лучше заменить.

## 7. Проверки в репозитории

Перед релизом полезно выполнить:

```powershell
git grep -n -I -E "service_role|VETMO_SYNC_SERVICE_KEY|VETMO_SYNC_STRATZ_TOKEN" -- .
git grep -n -I -E "eyJ[A-Za-z0-9_-]{20,}|sb_secret_|sbp_[A-Za-z0-9]+" -- .
git check-ignore -v .env secrets.env api.txt
```

Первые две команды показывают только имена переменных и документацию,
но не реальные значения. Секретные файлы должны быть в `.gitignore`.
